# Schema v2: Cross Structure and Lineage

Design doc for extending the genetics Excalidraw scripts from "isolated genotypes" (v1) to "connected lineages of genotypes via crosses" (v2). Captures schema, the DAG architecture, the Tidy lineage-walk algorithm, the new Cross script flow, and the v1 to v2 migration path.

Companion reading: `references/mindmap-kb/` documents the mindmap-builder script whose architecture informed several decisions here. Sub-agent porting suggestions are in `references/mindmap-kb/99-subagent-porting-suggestions.md` (advisory, not load-bearing).

---

## Goals

1. Make a **cross** a first-class concept: two parental genotypes linked to one or more offspring via an `x` glyph and lineage line.
2. Support **multi-generation lineages**: an offspring of one cross can be a parent in the next.
3. Support **selection criteria** as inline annotations on the cross arrow ("non-Tb, Sb/+").
4. Support **labeling** of individual instances ("M1.1, M1.2") for the single-fly/recombination workflow where multiple offspring share a genotype string but are tracked separately.
5. Keep the **single-source-of-truth principle**: relationship data lives on the offspring; the visual furniture (`x` glyph, lineage line, criterion text) is regenerated by Tidy.

## Non-goals (deferred to v3 or later)

- Mendelian cross resolver (auto-compute offspring genotype from parents).
- Stock library lookup integration.
- "Link Parents" retrofit script for setting parents on genotypes built before they had upstream crosses on the canvas.
- Recursive incremental Tidy (Tidy walks the connected lineage but doesn't try to do partial updates).
- Backwards rendering to markdown / outline form.

## Schema (v2)

Every element of a genotype or cross carries `schemaVersion: 2` plus a `kind`. Element kinds are flat (no nesting). The `genotypeId` is a UUID generated at Build time and preserved across Tidy regenerations (per v1 behavior). Native Excalidraw element ids regenerate on Tidy.

### Genotype member elements

```js
// Sex glyph (optional, one per genotype)
{ schemaVersion: 2, kind: "genotype-glyph",
  genotypeId,
  parents?: { maternal: id|null, paternal: id|null } }

// Allele text (one per allele)
{ schemaVersion: 2, kind: "genotype-allele",
  genotypeId,
  chromosome: "X" | "II" | "III" | "IV",
  side: "single" | "top" | "bottom",
  parents?: { maternal: id|null, paternal: id|null } }

// Fraction line (one per heterozygous chromosome)
{ schemaVersion: 2, kind: "genotype-fraction",
  genotypeId,
  chromosome: "X" | "II" | "III" | "IV",
  parents?: { maternal: id|null, paternal: id|null } }

// `;` separator (one per chromosome boundary)
{ schemaVersion: 2, kind: "genotype-separator",
  genotypeId,
  after: "X" | "II" | "III",
  parents?: { maternal: id|null, paternal: id|null } }

// NEW: optional human-readable label
{ schemaVersion: 2, kind: "genotype-label",
  genotypeId,
  text: "M1.1",
  parents?: { maternal: id|null, paternal: id|null } }
```

The `parents` field is **absent** on root genotypes (stocks, founders) and **denormalized across every element** of an offspring genotype (same rule as `genotypeId`).

### Cross furniture elements

```js
// The `x` glyph between two parents (one per unique parent pair)
{ schemaVersion: 2, kind: "cross-glyph",
  parents: { maternal: id, paternal: id } }

// Lineage line segment (one per parent-pair to child connection)
{ schemaVersion: 2, kind: "cross-lineage",
  childGenotypeId }

// Optional selection criterion text (one per child, when supplied)
{ schemaVersion: 2, kind: "cross-criterion",
  childGenotypeId,
  text: "non-Tb, Sb/+" }
```

### Field-level notes

- `parents.maternal` and `parents.paternal` may each independently be `null` if the role is unknown or irrelevant. The whole `parents` field is **absent** (not `null`) on root genotypes; this enables the cheap root check `customData.parents === undefined`.
- `parents` is not stored on `cross-*` elements; the `x` glyph carries the pair directly, and `cross-lineage` / `cross-criterion` use `childGenotypeId` to identify the edge.
- `cross-glyph` is keyed by the parent pair. Selfing (`maternal === paternal`) is allowed; Tidy renders it as a single edge looping from the parent to itself-via-offspring rather than two parallel edges.
- `cross-lineage` represents one edge: from the `x` glyph (identified by the offspring's `parents`) to one specific offspring (identified by `childGenotypeId`). When a cross has N offspring, there are N `cross-lineage` elements. Tidy decides whether to draw them as separate lines or merge into a tree with a shared trunk; either way, each line carries the `childGenotypeId` of the leaf it terminates at.
- `cross-criterion` is optional and per-child. Different offspring of the same cross may have different criteria.

### Element kind summary table

| kind | per | required fields beyond schemaVersion | optional |
|---|---|---|---|
| `genotype-glyph` | genotype (≤1) | `genotypeId` | `parents` |
| `genotype-allele` | allele | `genotypeId`, `chromosome`, `side` | `parents` |
| `genotype-fraction` | het chromosome | `genotypeId`, `chromosome` | `parents` |
| `genotype-separator` | chromosome boundary | `genotypeId`, `after` | `parents` |
| `genotype-label` | genotype (≤1) | `genotypeId`, `text` | `parents` |
| `cross-glyph` | parent pair (1 per cross) | `parents` (both required) | none |
| `cross-lineage` | offspring edge (1 per cross-to-child) | `childGenotypeId` | none |
| `cross-criterion` | offspring edge (≤1 per cross-to-child) | `childGenotypeId`, `text` | none |

## DAG architecture

A lineage is a directed acyclic graph (DAG), not a tree. Multiple parents per node (always exactly two), and a single genotype id may serve as a parent in many downstream crosses. The schema is already DAG-friendly; the implications live in the algorithms.

### Walk algorithms

Every traversal (ancestor walk, descendant walk, lineage collection) carries a `visited: Set<genotypeId>` and bails when re-entering a visited id. This is cheap and handles:

- Diamonds: F1 self-cross where both parents are the same F1 cohort, so two paths reach the same ancestor.
- User-error cycles: data corruption where someone hand-edited customData and produced a cycle. The walker terminates gracefully rather than infinite-looping.
- Selfing: `parents.maternal === parents.paternal`.

### Generation depth

Y-coordinate in Tidy is assigned by **generation depth** computed as the longest path from any root to the node. A node reachable via a length-2 path through one ancestor and a length-3 path through another sits at depth 3 (the longest). This ensures all parents of a node sit strictly above it.

```
computeDepth(genotypeId):
  if depth[genotypeId] cached: return it
  if parents absent: return 0
  d = 1 + max(computeDepth(parents.maternal), computeDepth(parents.paternal))
  cache and return d
```

(Visited-set guards omitted for clarity; required in production for cycle safety.)

### Layered DAG layout

Within each generation (same depth), nodes are ordered horizontally to minimize edge crossings. For the small pedigrees this script targets (typically <20 genotypes), a barycenter heuristic over a few sweeps is sufficient; no need for a full Sugiyama implementation. The layout pipeline:

1. From the user's selection, walk to all ancestors (collect roots).
2. From roots, walk down via descendant queries (find offspring whose `parents` reference any genotype in the set), expand to fixpoint.
3. Compute `depth[id]` for every collected genotype.
4. Bucket genotypes by depth.
5. Within each bucket, order by barycenter of parent x-positions (top down), then refine with a bottom-up sweep.
6. Assign x-coordinates within each bucket; assign y-coordinates by depth * generation_gap.
7. Render `x` glyph for each parent pair: between the two parents' positions, midpoint x, depth-aligned y.
8. Render `cross-lineage` from each `x` glyph to each offspring.
9. Render `cross-criterion` (if present) adjacent to its lineage line at midpoint, offset right.

## Scripts

### `Build Genotype` (v1.5: minor v2 update)

Existing v1 behavior + writes `schemaVersion: 2`. No `parents` field emitted (Build always creates roots). Otherwise unchanged.

### `Cross Genotypes` (new)

Creates an offspring of two selected parents.

**Preconditions:**
- Excalidraw selection contains elements from exactly two distinct genotypes. Resolve each selected element to its `genotypeId`; the unique set must have size 2. Error otherwise.

**Maternal/paternal assignment:**
1. If both parents have a `genotype-glyph` element with a sex character, assign: `♀` to maternal, `♂` to paternal. `☿` (virgin female) counts as `♀`. `⚥` is ambiguous.
2. If exactly one parent has a clear sex glyph, assign that and put the other in the opposite role.
3. If neither has a clear glyph, default to maternal = leftmost (lower x-coordinate of the centroid).

The assignment is stored in `parents` and can be swapped later via a future "Swap Parents" action (deferred to v2.1).

**Prompts:**

The prompt header reconstructs each parent's shorthand for visibility:

```
Cross: ♀ w; +/+; TM3/+   ×   ♂ +; If/CyO; +
```

Then sequentially prompts:
1. Sex glyph for the *offspring* (suggester, same options as Build).
2. Offspring genotype shorthand (input prompt, same parser as Build).
3. Optional label (input prompt, blank to skip).
4. Optional selection criterion (input prompt, blank to skip).

**Creation pipeline:**
1. Generate `genotypeId` (UUID).
2. Build offspring elements via the same logic as Build, stamped with `parents: {maternal, paternal}` on every element.
3. If label provided, create `genotype-label` element.
4. Find existing `cross-glyph` for this parent pair: if present, reuse; else create one tagged with `parents`.
5. Create one `cross-lineage` element tagged with `childGenotypeId`.
6. If criterion provided, create `cross-criterion` element tagged with `childGenotypeId`.
7. Position offspring elements at midpoint x of parents, below the lower parent. (Tidy run immediately afterwards will lay out properly.)
8. Group all new elements (offspring + furniture) and add to view.
9. Auto-run Tidy on the lineage.

**Adding another offspring to an existing cross:** running Cross with the same two parents selected reuses the existing `cross-glyph` (lookup by parent pair) and adds a new `cross-lineage` plus offspring.

### `Tidy` (renamed and expanded from `Tidy Genotype`)

Operates on the **connected lineage** containing the user's selection.

**Algorithm:**

```
1. Identify start genotype from selection (resolve element -> genotypeId).
2. Walk ancestors (DFS with visited set) using parents.maternal / parents.paternal.
   Stop at nodes where parents field is absent (roots).
3. From the ancestor set, walk descendants:
   - For each genotype in the current set, find all genotypes whose
     parents.maternal or parents.paternal is in the set.
   - Add them; repeat until fixpoint.
4. Collect every element with genotypeId in the lineage set, plus every
   cross-glyph whose parents.{maternal,paternal} pair is within the set,
   plus every cross-lineage / cross-criterion whose childGenotypeId is in the set.
5. Compute generation depth for each genotype.
6. Bucket by depth. Order within bucket by barycenter sweep.
7. For each genotype: reflow its internal layout (same as v1 Tidy Genotype).
   Honor manual edits to allele/label/criterion text.
8. Place genotypes at computed (x, y).
9. Place cross-glyph for each parent pair: midpoint between parents,
   slightly above the offspring row.
10. Draw cross-lineage as a line from the cross-glyph down to the offspring.
    If multiple offspring share a cross, draw a branching tree (single trunk,
    fanning to each offspring), with each branch terminating at one offspring
    and tagged with that childGenotypeId.
11. Place cross-criterion adjacent to its lineage line, offset right of midpoint.
12. Genotypes outside the connected lineage are left untouched.
13. As elements are regenerated, do not invalidate genotypeIds. Excalidraw
    element ids may regenerate (v1 behavior preserved).
```

The trivial case (isolated genotype, no parents, no descendants) collapses to v1 `Tidy Genotype` behavior with no extra cost.

## Migration v1 to v2

Lazy. Triggered the next time Tidy operates on a v1 genotype.

**On Tidy of an element with `schemaVersion: 1`:**
1. For each element in the genotype, update `schemaVersion` to 2.
2. Do not add a `parents` field (v1 genotypes have no upstream cross by definition; they are roots).
3. Run Tidy normally.

**No standalone migration script.** Documents with both v1 and v2 genotypes are valid; mixed-version reads should treat v1 elements as roots (no parents).

**Forward compatibility:** the script always writes `schemaVersion: 2`. Reading code should fail closed on `schemaVersion > 2` with a clear error pointing to the script version.

## Helpers worth implementing once

- `getGenotypeIdFromElement(el)`: resolves any tagged element to its `genotypeId`. Handles all genotype-member kinds; returns null for cross furniture.
- `getGenotypeElements(genotypeId, allElements)`: collects every element with that `genotypeId`.
- `reconstructShorthand(genotypeId, allElements)`: inverse of `parseShorthand`. Iterates allele elements by chromosome and side, joins with `/` and `;`. Used in Cross prompt header, label auto-derivation (if added later), and any "show this genotype as text" feature.
- `getCross(parentPair, allElements)`: finds the `cross-glyph` (if any) matching a `{maternal, paternal}` pair.
- `walkAncestors(genotypeId, allElements, visited?)`: DAG-safe ancestor collection.
- `walkDescendants(genotypeId, allElements, visited?)`: DAG-safe descendant collection.
- `collectLineage(genotypeId, allElements)`: ancestor + descendant fixpoint. Returns the connected-lineage set.
- `computeDepth(genotypeId, depthCache, ...)`: memoized longest-path-from-root.

Build them as plain functions, threaded with an `allElements` argument rather than closure-captured globals. Pattern is the same as mindmap-builder's `elementById` / `parentMap` / `childrenMap` precomputed maps (see `references/mindmap-kb/05-notable-idioms.md`).

## Open questions deferred to v3+

- **Cross resolver:** Mendelian math to compute offspring genotype from parents. Requires a balancer/marker database (mentioned in README roadmap). Will likely surface as a "Compute Offspring" button in the Cross prompt that prefills the shorthand.
- **Stock library lookup:** suggester for parent genotypes from stock-note frontmatter in the vault. Bypasses manual entry for common stocks.
- **Link Parents:** retrofit script for genotypes drawn separately before being part of a cross. Lets user select an offspring and two parents and stamp the relationship.
- **Swap Parents:** action to swap maternal and paternal assignment without retyping.
- **Recursive Tidy with manual-position respect:** v2 Tidy regenerates positions; a future variant could honor manually-positioned ancestors as anchors and only re-tidy descendants.
- **Markdown export of a lineage:** outline form for inclusion in lab notes. Probably never needed; flagged here so it doesn't sneak back in.
